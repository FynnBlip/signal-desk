# ADR-004 · 手机与蓝牙麦克风的真实人声采集（08 真机采集）

- 状态：已实现最小闭环（模块级 + HTTP 级自检通过）
- 日期：2026-09-21
- 模块：`modules/08_capture/`
- 关联：README 数据红线、`docs/验收清单.md`、豆包评审的五点顾虑

## 1. 背景：要解决的不是「再加一个录音按钮」

Signal Desk 的 01–06 全部建立在 **MiniMax 合成语料** 上。这带来三个必须正面回答的问题：

| 顾虑 | 真机采集对应的回答 |
|---|---|
| 合成语料的生态效度 | 真机语料是**证据层**：合成基准得出的 ΔPQ 方向，在真机语料上是否同向 |
| 评测工具可靠性没有自证 | 电平时标定 + 断档记账 + 设备指纹留痕，让「这次测量可不可信」变成可读的数字 |
| 目标用户与可体验性 | 手机扫码即可采，不需要装环境、不需要买设备 |

反面选项（被否掉）：把真机录音直接塞进 `data/matrix/` 当作新语料。那样 Loop 的晋级结论会同时依赖两种完全不同方差的输入，Gate 的判据立刻失效。

## 2. 决策

### D1 · 采集走 AudioWorklet 原始 PCM，禁用 MediaRecorder

`MediaRecorder` 输出 webm/opus 是有损二次编码，等于在 DUT 前面又插了一个编解码器，破坏「一份数据一个唯一来源」。
实现：`AudioWorkletProcessor` 只做搬运（不做增益、不做滤波），主线程把 Float32 转 Int16 后按 1 秒分片 POST 二进制体，服务端拼接并落 `raw/mic.pcm` → `raw/audio.wav`。

### D2 · AEC / NS / AGC 必须显式关闭，并**回读实际值**

浏览器默认开启 `echoCancellation` / `noiseSuppression` / `autoGainControl`。其中 NS 相当于在 DUT 之前串了另一个降噪器，AGC 让电平不可复现 —— 这两项一旦开启，测出来的 ΔPQ 全部无意义。

- 请求：三项全部 `false`，`channelCount: 1`。
- 回读：`track.getSettings()`，写入 `client_manifest` 并进入 Trace。
- 定级：
  - `grade_c` — NS 或 AGC 实际为 `true`，或有效时长 < 1s。**只保留取证，禁止使用。**
  - `grade_b` — 无法关闭 AEC / 丢帧 / 削波 / **实际状态未知**。仅作探索试听。
  - `grade_a` — 三项实际关闭 + 无丢帧 + 无削波。可进入比较。
- **未知不等于干净**：浏览器不回报状态时按 `grade_b`，而不是默认通过。

### D3 · 真机语料是独立 tier，Gate 禁止跨 tier 晋级

```
synthetic_tts  ──→ Loop 晋级判定（唯一允许决定晋级/回滚的 tier）
real_device    ──→ 生态效度校验报告（只回答「合成结论在真实链路上是否同向」）
```

`cross_tier_gate()` 拦截混用；`validity_compare()` 比较两个 tier 上 ΔPQ 的**方向一致性**。
方向不一致不等于谁错，等于基准的生态效度存疑，需要人来看 —— 这才是这个能力真正的价值点。

> **落位现状（2026-09-22，必须如实说明）**：`cross_tier_gate()` 目前只是一个**可被主动调用的查询接口**
> （`POST /api/capture/tier-gate`），**没有接在 07 闭环大脑的晋级入口上** —— `modules/07_loop/loop.py`
> 与 `modules/06_evaluate/evaluate.py` 中 `tier` 一词零命中。也就是说「Gate 禁止跨 tier 晋级」当前是
> **函数 + 文档承诺**，不是运行时强制。
> 今天混不进去，靠的是「08 是旁挂模块、真机语料没有任何自动流入 07 的通路」，
> 而不是「接了也拦得住」。把门禁接进 07 的晋级入口属于改动 01–07，不在本次落位范围内，
> 列为后续必做项：在 07 构造 sources 的地方强制调用，未通过直接 raise，并把 `tier_set` 持久化进 run 记录。

### D4 · 蓝牙 HFP 被建模成 channel condition，不是缺陷

蓝牙耳机的 HFP 麦克风是窄带（典型 8/16 kHz 采样、300–3400 Hz 通带）。真实通话大量走这条路，把它当缺陷等于放弃最重要的真实场景。

- 输入路径必须**显式声明**：`phone_internal` / `bluetooth_hfp` / `bluetooth_le` / `wired_headset` / `usb_mic` / `unknown`。
- 新增 `hf_ratio_db`（4 kHz 以上能量占比）作为**带宽指纹**：窄带链路的该值显著低于宽带，可用于事后校验「你说这是内置麦，但数据看着像蓝牙」。
- 规则：**跨 input_route 的结果不可直接比较**，同 route 内可比。

### D5 · 网络接入：优先 Tailscale Serve，自签证书作为兜底

浏览器只在**安全上下文**下开放麦克风。手机访问 `http://192.168.x.x:8090` 会被直接拒绝（`navigator.mediaDevices` 不存在）。方案对比：

| 方案 | 手机端要做什么 | 真证书 | 能否远程 | 结论 |
|---|---|---|---|---|
| **Tailscale Serve** | 装 Tailscale 登录同一 tailnet | 是 | 是 | **推荐主路径** |
| 本机自签证书（IP SAN） | 装根证书 + 开启完全信任 | 否 | 否 | 离线内网兜底 |
| Cloudflare Tunnel / ngrok | 无 | 是 | 是 | 备选，注意别把实验台暴露到公网 |
| 原生 App / Termux + ffmpeg | 装 App | 不涉及 | 否 | 保真度最高，门槛也最高 |
| 手机录音 App → 导入 WAV | 无 | 不涉及 | 不涉及 | **零门槛兜底**，但无设备指纹、无断档检测 |

自签证书由 `scripts/serve.py` 用 openssl 生成（SAN 含所有局域网 IP 与本机名），并与一次性配对令牌一起使用。

### D6 · 真机语料带 PII，默认不出本地

- Trace 只写 `speaker_code`（如 `SPK-01`），**不写姓名**。
- `session.json` 带 `consent` 三元组：说话人是否知情、是否本地留存、是否允许公开分享。默认 `allow_public_share=false`。
- `data/` 不入库；对外分享样例必须另有授权。

### D7 · 本版不做实时回环（明确边界）

「边说话边听 DUT 输出」需要 WebSocket 双向流 + 服务端实时推理 + 抖动缓冲，工程量和误用风险都高。V0.1 只做**引导式干采集**：手机负责采，桌面工作台负责跑参数扫描与盲听。
实时回环列为 V0.2，前置条件是先证明干采集链路的时间戳与电平可信。

## 3. 接口契约

### 目录（`data/real_capture/`）

```
sessions/<session_id>/
  session.json          # 不可变身份记录（说话人代号、脚本、路径、tier、consent）
  capture_state.json    # 运行态（已收段数、断档序号、丢帧数）
  session_result.json   # 封存后写一次，之后不可重写
  raw/mic.pcm           # 唯一来源，落盘后不可改
  raw/audio.wav         # 同一份数据的无损封装
capture_runs_v1.csv     # append-only trace，固定 schema
```

### Trace schema（v1，加字段必须升版本）

```
schema_version, session_id, created_at, finalized_at, speaker_code, script_id,
declared_route, detected_label, input_device_id, sample_rate, channel_count,
aec_requested, aec_actual, ns_requested, ns_actual, agc_requested, agc_actual,
chunk_count, chunk_gap_count, dropped_frames, duration_s, rms_dbfs, peak_dbfs,
clip_ratio, dc_offset, voiced_ratio, hf_ratio_db, wav_sha256, pcm_sha256,
capture_grade, usable_for_loop, notes
```

### 引导脚本（内置）

| id | 类型 | 作用 |
|---|---|---|
| `anchor` | anchor ×3 | 跨会话电平标定 + test-retest 稳定性自检的输入 |
| `p1` / `p2` | speech | 常规与长句可懂度 |
| `p3` | fricative | 擦音/齿音探针，专抓降噪器吃高频 |
| `p4` | silence | 静音探针，看本底噪声与 musical noise |

### HTTP 接口

```
GET  /api/capture/scripts
POST /api/capture/session                          # 建会话
POST /api/capture/session/{id}/chunk?seq=&frames=  # 原始 int16le 二进制体
POST /api/capture/session/{id}/finalize            # 封存 + 定级 + 写 trace
GET  /api/capture/session/{id}
GET  /api/capture/sessions
GET  /api/capture/summary
GET  /api/capture/audio/{id}
POST /api/capture/validity                         # 生态效度方向一致性
POST /api/capture/tier-gate                        # 跨 tier 门禁
```

## 4. 后果与待验证项

已验证（并入工作台后复验，2026-09-22）：
- 采集与定级：`18` 项模块单测通过；并入后仓库全量 `101` 项单测通过；端到端自检（模块级 + HTTP 级）`8/8` 通过。
- 丢帧被如实记账（`dropped_frames` + `gap_seqs`），不静默补齐。
- 封存不可重写；Trace 只增不改（32 列与 `TRACE_FIELDS` 一致）；含 `..` 的 `session_id` 返回 400。
- 带宽指纹可区分宽带与 4 kHz 以上被截断的窄带信号。
- 令牌守卫在请求层 fail-closed：绕过 `__main__` 用 `uvicorn main:app --host 0.0.0.0` 且不设令牌时，
  经局域网 IP 访问 `/api/capture/*` 实测返回 `403`，回环访问仍为 `200`。

## 5. 首次真机实测记录（2026-09-23）

设备：小米 14（`23127PN0CC` / houji），Android 15，MIUI 浏览器（Chromium 135 内核）。
接入方式：**`adb reverse` 无线调试**，手机访问 `http://localhost:8090/capture.html`。

### 已被真机坐实的结论

| 项 | 结果 |
|---|---|
| `localhost` 构成安全上下文，麦克风可用 | ✅ `secure_context=true`，**全程零证书** |
| `adb reverse` 在**无线调试**下同样可用 | ✅ 手机侧 `curl localhost:8090` 返回 200 |
| `getSettings()` 回报 AEC/NS/AGC | ✅ 三项均回报 `false`（该浏览器覆盖率良好） |
| `grade_a` 判定可在真机达成 | ✅ `capture_grade=grade_a`，三项实测全 `false` |
| 无线链路下的传输完整性 | ✅ 36 chunk，`chunk_gap_count=0`，`dropped_frames=0` |
| 客户端上传失败计数 | ✅ `client_upload_failures=0` |

会话指标：`duration_s=32.995`、`rms_dbfs=-31.58`、`peak_dbfs=-0.38`、
`clip_ratio=0.0`、`voiced_ratio=0.2684`、`hf_ratio_db=-5.87`。

### 实测暴露的三个问题

1. **声明路径与带宽指纹不一致（待查）**：本次 `declared_route=bluetooth_hfp`，
   但 `hf_ratio_db=-5.87` 是宽带特征；若真走 HFP 窄带（8 kHz，4 kHz 以上被截断），
   该值应在 -20 dB 量级。最可能的解释是**耳机听筒走 A2DP、麦克风仍是机身麦**
   （Android 未显式激活 SCO 时的常见行为）。
   **尚未完成内置麦对照录制，因此无法定论**——这正是 D4 带宽指纹要抓的场景。
2. **`detected_label` 为空**：该浏览器不暴露 `track.label`，导致无法独立佐证输入路径。
   附带效果是 D6 担心的「设备名带真名」风险在本机未发生，但这是浏览器行为，不可依赖。
3. **`peak_dbfs=-0.38`**：距削波仅 0.38 dB。页面缺少录制前的电平预检与过载提示。

### 本次仍未验证

- **Windows 平台整体未验**（开发与验证均在 macOS + Python 3.11；项目声明 Windows + 3.12）。
- **iOS 完全未验**（Safari 的 `getSettings()` 覆盖率、自签证书信任流程均未走过）。
- **内置麦 vs 蓝牙麦的 `hf_ratio_db` 对照未完成**。
- **stock Chrome 未验**（本次为 MIUI 浏览器；虽同为 Chromium 135 内核，但不等价）。
- 严重-4 修复（改用 `AudioContext.sampleRate` 而非 `track.getSettings().sampleRate`）
  **未被本次实测区分**：该机上两值均为 48000，恰好一致，分歧场景仍未覆盖。

待验证（不写进「已完成」）：
1. **真机实测**：iOS Safari 与 Android Chrome 上 `getSettings()` 的回报覆盖率。回报不全时会落到 `grade_b` —— 这是设计意图，但需要实测确认它不会把大多数手机都拦掉。
2. **test-retest 稳定性**：同一设备重复读 anchor 3 次的 ΔPQ 分布与置信区间，需要 06 评测跑完才能给出。模块 08 只保证输入侧可标定（电平 + 带宽 + 断档）。
3. **耳机回环串扰**：蓝牙耳机在免手持通话时可能触发耳机侧 AEC，与 `getSettings()` 的回报不一致，需实测比对 `hf_ratio_db` 与 `aec_actual`。
